StudyMates — common four-member plan

This is the current team working plan. It supersedes the five-member assignments and startup assumptions in the two original StudyMates guides. It is not an assignment report. Deliverable: five-minute live Android demonstration, with no slides, report or formal rubric. All four members use VS Code with Codex.

Read this first, then your individual guide:

1. What we are building

StudyMates helps people find study partners through SIG → subgroup → room → focus session → personal history. Example: IoT → ESP32 → First Sensor Project. The timer records eligible participation, not verified attention or learning.

Core target: email/password accounts and reset, preset profiles, create/discover/ join/leave SIGs, owner-created subgroups, six-seat rooms, personal goals, a shared focus/break schedule, one completion per user/session, camera invitations with manual fallback, and private personal history. Retain camera scanning as a product choice; do not describe it as a formal marking criterion now that no rubric exists.

Normal schedule: 25-minute focus + 5-minute break. Provide a visibly labelled 60-second demo cycle, kept separate from ordinary progress. Proposed demo split: 45-second focus + 15-second break; agree and record the exact split at Gate 1. Goal outcome (completed/unfinished) is independent of timer completion.

Defer charts, decorations and resource links until the connected path is reliable. No full chat, voice/video, AI, 3D world, uploads, public rankings or public launch.

6. Working together in Git and Codex

Use one repository, one clone per person, and short task branches. Before a task, check git status; preserve unfinished changes. With a clean tree and the shared baseline merged, use git switch main, git pull --ff-only, then git switch -c feat/<one-small-task>. No force-pushes over shared work, duplicated apps, bulk replacement of folders, or automatic resolution of others' conflicts.

One small issue should name the owner, allowed files, input contract/commit, observable success/error cases, reviewer and any shared-file reservation. Every day (or after each work block), post: branch, completed, next, blocker, and requested handoff. This is team coordination, not a report deliverable.

Review assignments: Poojani and Aradhana review each other's backend/rules work; Shanuka reviews UI/integration; Sandali reviews QR/history consumers; Poojani reviews Shanuka's app wiring/release. Each PR needs one appropriate human reviewer and matching checks. Feature owners must explain the behavior their AI helped produce.

7. Reliability and scope decisions

Use atomic admission for six seats and one active seat per user; enforce permissions in backend rules, not just button visibility. Use shared timestamps rather than per-second timer writes. Document late-join/early-leave credit, lease/grace periods, uncertain connectivity, background/resume and host departure. Finalizing the same user/session twice must not produce a second completion. History is private.

Poojani owns the shared development Firebase project; collaborators use their own accounts. Never put admin credentials, release signing secrets or passwords in source or AI prompts. Client config is distinct from admin secrets; decide its tracking policy explicitly. Do not use allow-all shared database rules. Human project setup/rule deployment is a named step, not an implicit action in every prompt.

If a gate slips, stop charts/decorations/resources and final art polish. Shanuka helps with a bounded integration task; he does not absorb all unfinished features. If Sandali is overloaded, finish the camera spike first, then the minimal history list/total; Shanuka can take history presentation after an explicit ownership transfer. If Aradhana is overloaded, Poojani pairs on transactions after accounts are stable and Shanuka retains all session UI. Transfer a named file/task before another person or Codex agent edits it.

Use a visible demo flag and a separate demo-history view/dataset; normal totals must exclude demo time. A backup recording may explain an outage but must not be represented as live behavior.
